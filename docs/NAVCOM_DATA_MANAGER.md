# M2-G-A2 — explicit first route-data installation

This draft stacks on accepted converter PR #12, which stacks on unmerged M2-F PR #11. It adds a missing-data **NAVCOM Route Database** panel. Click **Load route data**, then, if absent, **Download Route Data**. There is no startup/module-open/sign-in download, periodic update, latest-build lookup, credential change or ESI side effect. Existing Load/Retry and offline routing remain independent.

The intentional action requests approximately 99 MB from the single compiled official CCP source:

`https://developers.eveonline.com/static-data/tranquility/eve-online-static-data-3662168-jsonl.zip`

Build **3662168** and the reviewed archive, two table and snapshot digests/counts remain exactly those in [SDE_IMPORT.md](SDE_IMPORT.md) and the existing compiled frontend pin. No arbitrary URL, path, digest, pin or credentials can be supplied by the renderer. The native command uses only the validated PortableStore root. A neighboring provenance file cannot grant trust.

## Native data flow and limits

Only release Windows builds may fetch the real archive. Debug/test builds and other platforms refuse before HTTP; synthetic tests use an internal injected transport/pin, absent from IPC. The fixed HTTPS client retains normal native CA trust/proxy settings, disables redirects and retries, adds no credential/cookie headers, and has a 10-second connect / 120-second total timeout. Only status 200 is accepted; 429/offline/truncated/error responses fail explicitly. Declared and actual streamed size are capped at 256 MiB, including chunked responses; allocation grows within that cap and allocation failure is reported. Raw archive bytes stay in native memory and are dropped after conversion; they are never staged to disk or logged. OS paging/crash-dump policies are outside this application's memory-storage guarantee.

A1's sole production converter verifies the archive hash/build and bounded format/topology. A2 additionally requires the exact snapshot digest, both table digests and counts (8,490 systems, 13,978 reciprocal gates, 6,989 edges, 3,222 isolated). No mirror, new build or synthetic production fallback. The current archive BODY and real production conversion have **not** been tested in Codex or CI. Historical HEAD availability does not verify the current payload.

The UI reports real native phases (downloading, verifying/converting, installing, ready/error), with no invented percentages. During a user-started operation only, a separate argument-free local status IPC is polled every 400 ms; it causes no network request. The bounded operation is not cancellable through the panel. Leaving the module does not undo an explicit operation or an already published file. There are no automatic retries; the user decides whether to retry after a failure.

## Storage, publication and recovery

Only `<standalone-executable-folder>/app-data/navcom/snapshot.json` is published. Use a local extracted folder outside source control, build targets, shared or cloud-synced storage. Production refuses Git ancestors, `target`, known sync-folder names/configured OneDrive roots, system temporary/AppData roots, UNC/nonlocal drives and all links/reparse points observed by the existing no-follow directory checks. Ordinary filesystems do not expose every third-party sync/upload agent, so **the owner must ensure the chosen portable folder is private and not synced**. There is no fallback to AppData/home/temp/CWD and no path picker.

The existing process-lifetime PortableStore OS lock excludes a second normal app instance. A shared native single-flight guard excludes reentrant IPC. A mutation DirectoryGuard reuses the reader's directory identity rules, retains all ancestor/target directory handles and checks them around mutation; the reader's existing read behavior is unchanged. On Windows these retained handles deny rename/delete. On Linux device/inode checks detect observed swaps; the inherited same-user trust boundary is not a formal sandbox against an adversarial process with the same identity.

Existing data is read first through the safe fixed reader. Exact approved snapshot bytes return already-installed without HTTP or writes. Corrupt, unreadable, unsafe or unsupported existing data is preserved and refused. Nothing is repaired, removed or overwritten. Even after the initial absence check, the final publication primitive atomically refuses a racing destination.

Only the converted snapshot is staged, under an unpredictable create-new `.route-install-<random>.tmp` name in the guarded `navcom` directory. On Unix it is mode 0600; on Windows it has a protected owner-rights DACL, read/write/DELETE access and exclusive sharing. It is written, flushed and read back to verify length/hash before publication. Windows renames the held source object with `SetFileInformationByHandle(FileRenameInfo)`, `ReplaceIfExists=FALSE`; it does not rename an attacker-replaceable source path. Linux tests link the held inode via kernel procfs using `linkat` into the held directory, with no-clobber semantics, then remove only the identity-matched staging entry and sync the directory. Missing procfs/hard-link support or an unsupported primitive fails closed, with no naive rename/overwrite fallback. Other production platforms are disabled.

Normal cleanup is explicit and checked; destructor cleanup is a fallback. Windows deletion targets only the owned handle. Linux cleanup verifies directory and staging-file identity, and preserves a replacement path rather than deleting it. If cleanup cannot be proven safe, it leaves bytes for recovery and reports failure where observable. A process/power interruption can leave a private staging file; it is never read as a snapshot or automatically promoted. Do not blindly delete similarly named files. Preserve the portable folder and inspect exact owned temporary data before manual recovery. Raw archives are never left there.

The final safe native read rechecks published bytes, and then the frontend immediately calls the unchanged `readNavcomSnapshot()` to perform compiled SHA/schema/graph validation and reveal the planner without restart. If a racing valid snapshot was installed or a post-publication error occurred, **Retry loading** can recover it. No rollback deletes an existing or published snapshot. Existing settings/Appearance files and themes are untouched. Move the whole portable folder only after closing the app.
