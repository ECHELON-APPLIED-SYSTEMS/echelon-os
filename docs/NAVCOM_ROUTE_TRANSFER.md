# M2-H — transfer planned waypoints

This draft stacks on PR #13, with no changes to dependency PRs #11–#13. After calculating a static minimum-hop route, **Set Route in EVE…** offers a separate expiring native confirmation. It shows character name/ID, origin/target, jump count, operation count and the ordered systems after origin. Calculation, opening NAVCOM, login and location updates never send waypoints.

The first POST sends the first system **after origin** with `clear_other_waypoints=true`; remaining POSTs append in sequence with `false`. Every request uses `add_to_beginning=false`. Existing Set Destination/Add Waypoint remain separate. The feature transfers intended waypoints; it neither activates autopilot nor controls a ship. EVE preferences/avoidance/dynamic topology may produce different paths between waypoints. It is not gate control, a safest route or live risk intelligence.

## Fixed application limits and public preflight

Bounded unauthenticated official OpenAPI and rate-guide reads were performed; no login, location request, game data download or ESI write was used. The schema retained compatibility version `2026-08-18`, the existing waypoint endpoint/scope/query flags, 204 response and `x-rate-limit` metadata for group `ui`: **900 tokens per 15 minutes**. The official [rate guide](https://developers.eveonline.com/docs/services/esi/rate-limiting/) specifies 2 tokens for 2xx responses, Retry-After and remaining-token headers, with legacy error-budget behavior and possible deeper EVE-server 429s.

No authoritative client waypoint queue maximum was verified. These are deliberately conservative **application limits**, not a claim about EVE's maximum:

- At most **10 waypoint POSTs** (11 systems including origin). Longer routes are refused in full; use Set Destination instead. Never truncate silently.
- Serial HTTP only, **three seconds between requests**, no parallel writes or automatic retries. Pacing is split into cancellation-aware intervals.
- **120-second cooperative total work budget**, with at least one existing 20-second HTTP request allowance remaining before each send. File reads/library/OS work is not forcibly preempted.
- Reserve **10 UI tokens** beyond the two-per-request cost of all remaining operations. Known insufficient headroom prevents preparation/sending. If headroom is initially unknown, only the first explicitly confirmed request may be attempted; later sends require matching `ui` remaining-token headers. Missing/malformed headroom stops the prefix, rather than assuming unlimited capacity. Retry-After, 429 and exhausted legacy error budgets stop later requests. Header observations are not guarantees against concurrent server-side consumption.

These limits require a separately reviewed source change to revise after owner testing. No periodic reroute, movement trigger, route-risk data, new scopes, token persistence or registration change.

## Native authorization and cancellation

The renderer supplies a bounded candidate sequence, never URL/write flags/character/credentials. Its sequence deserializer rejects more than 11 IDs before unbounded vector growth. Native code re-reads the existing safe fixed snapshot, verifies the unchanged approved byte pin, validates schema/counts/order/names/edge references/isolation, checks every adjacent hop and recomputes ascending-neighbor BFS. The candidate must exactly match the deterministic current minimum-hop path. Arbitrary destination lists, detours, repeated/unknown IDs, same-system and disconnected routes fail closed. No adjacent provenance supplies trust.

A connected session and **fresh native ESI observation matching origin** are required. A mismatched manual origin is disabled with explicit refresh/use-current/recalculate guidance. There is no automatic location fetch. Confirmation expires at the earlier of **30 seconds or that observation's cache freshness end**; the official location cache can be only five seconds, so prepare/confirm promptly or explicitly refresh and recalculate. This strict initial policy can be reviewed later; freshness is never silently extended. A cached observation is not instantaneous proof that a ship remains there.

Confirmation binds native generation, character, exact path and location revision. Explicit refresh, connection change, expiry, other prepared waypoint intent and cancellation invalidate it. Before sending, native code consumes the nonce once, activates the transfer atomically under its state lock, and rechecks context. The snapshot/path is re-read/revalidated before **each** request. One native flight guard spans the transfer and pacing, preventing interleaved refresh/single-write/route operations. Disconnect remains available and prevents later sends; an already in-flight write can complete. Cancellation clears either the pending confirmation or active transfer without issuing ESI requests. Leaving the route view cancels remaining work where possible; its already sent prefix cannot be undone. Origin freshness is checked again before the first send; it is not polled or artificially renewed during the batch.

Only three typed main-local commands are added: prepare route, send confirmation, cancel confirmation/remaining work. Existing fixed HTTPS client, timeout, TLS/proxy, no-redirect/no-retry policy, portable reader, pin and authentication boundaries remain. Additional bounded rate headers stay native. No broad network/filesystem/CSP grant or external program.

## Results and acceptance limits

Every 204 increments an **API-accepted** prefix count, with last accepted ID. Reports distinguish all requests accepted, stopped, and unknown outcome; include an attempted failed/uncertain system separately from the next **never sent** system. 503/transport timeout/unusable response can have unknown effects. Stop at the first failure, without automatic resume, rollback or repeating the prefix. All-accepted is not proof the client applied an identical queue. Cancellation during the final in-flight 204 may still yield all requests accepted; nothing claims cancellation undoes it.

The confirmation warns that the first accepted write clears existing waypoints and partial delivery cannot be rolled back. **Inspect EVE's queue after any result before another request.** Endpoint edits/recalculation/reload are disabled while the session's transfer operation is busy. Leaving NAVCOM cancels later native sends but hides its local result panel; inspect EVE rather than assuming nothing happened. No route IDs, character details, tokens or graph are logged or published; test IDs/data are invented.

Synthetic native tests exercise flags/order, deterministic graph/schema/pin validation, fresh/mismatched origin, nonce expiry/cancel/replay, character/generation/revision changes, single flight, snapshot change, cap, pacing, time, rate headers/429/503/timeouts and prefix accounting. UI/service tests exercise explicit confirmation, no mount/rerender writes, disabled mismatch/stale/cap, cancel/change and partial results. Native ACL tests include remote/secondary denial for all three commands. Full native Linux Tauri prerequisites remain absent; no Windows run or live EVE/data acceptance was performed. Separate source review and owner approval are required for native validation, real queue acceptance, merges and releases.
